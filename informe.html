1. Introducción y Contexto

RetailSmart Chile SA es una cadena de retail nacional que comercializa productos de tecnología, vestuario y hogar a través de tiendas físicas, plataforma e-commerce y aplicación móvil. Ante la fragmentación de sus fuentes de datos (POS, ERP, CRM, logs, redes sociales) y la necesidad de implementar capacidades analíticas en tiempo real, se ha diseñado e implementado una arquitectura de datos moderna basada en contenedores Docker que materializa un pipeline ELT/ETL completo.

Este informe documenta la infraestructura técnica desplegada, los nueve microservicios que la componen, el modelo de datos dimensional implementado, la gestión de contratos de API mediante OpenAPI y los resultados analíticos obtenidos a partir de la simulación de datos transaccionales en un entorno corporativo bajo el protocolo visual GLITCHPOINT.

2. Arquitectura General del Sistema

La solución implementa una Arquitectura Lambda contenerizada sobre Docker Compose, que integra tres capas funcionales operando sobre una red interna aislada:

┌─────────────────────────────────────────────────┐ │ CAPA DE INGESTA Y FRONTEND │ ├─────────────────────────────────────────────────┤ │ srv-dashboard-cliente (Nginx + Vanilla JS) │ │ srv-api-backend (FastAPI :8000) │ └─────────────────────────────────────────────────┘ ↓ HTTP POST /ingest ↓ ┌─────────────────────────────────────────────────┐ │ CAPA DE ALMACENAMIENTO (DATA LAKE) │ ├─────────────────────────────────────────────────┤ │ srv-elt-pipeline (Python → MongoDB) │ │ srv-db-mongo-primary (Replica Set rs0) │ │ srv-db-mongo-replica │ └─────────────────────────────────────────────────┘ ↓ ELT Worker ↓ ┌─────────────────────────────────────────────────┐ │ CAPA DE TRANSFORMACIÓN Y ALMACÉN (DW) │ ├─────────────────────────────────────────────────┤ │ srv-etl-pipeline (Python → PostgreSQL) │ │ srv-db-postgres-primary (Star Schema) │ │ srv-db-postgres-replica │ └─────────────────────────────────────────────────┘ ↓ SQL Queries ↓ ┌─────────────────────────────────────────────────┐ │ CAPA DE CONSUMO (BI Y ANALYTICS) │ ├─────────────────────────────────────────────────┤ │ srv-dashboard-bi (Django + Jazzmin :8081) │ │ srv-cron-backup (Resguardo de datos) │ └─────────────────────────────────────────────────┘

Paradigma de Procesamiento: ELT (Extract, Load, Transform)

Se adoptó ELT en lugar de ETL tradicional debido a la heterogeneidad de las fuentes de datos (CSV, JSON, XML, logs, multimedia). El modelo ELT permite:

  • Ingerir datos crudos sin validación previa, preservando la trazabilidad histórica completa.
  • Desacoplar la fase de ingesta de la transformación, evitando cuellos de botella en servidores intermedios.
  • Re-transformar datos históricos cuando cambien los requerimientos analíticos sin perder información original.
  • Operar con esquemas de lectura posterior (schema-on-read) para datos semiestructurados y no estructurados.

3. Componentes y Servicios

srv-elt-pipeline Python + PyMongo — Worker autónomo. Poll cada 5s al API, extrae buffer y escribe eventos crudos en MongoDB (Data Lake).
srv-db-mongo-primary Bitnami MongoDB — Nodo primario del Replica Set rs0. Almacena eventos crudos sin transformación.
srv-db-mongo-replica Bitnami MongoDB — Nodo secundario del Replica Set. Proporciona alta disponibilidad y respaldo.
srv-etl-pipeline Python + SQLAlchemy + psycopg2 — Worker de transformación. Poll cada 10s, lee desde MongoDB, aplica Star Schema y carga en PostgreSQL DW.
srv-db-postgres-primary Bitnami PostgreSQL — Data Warehouse relacional. Almacena Fact_Ventas consolidada con dimensiones (Cliente, Producto, Tiempo, Canal).
srv-db-postgres-replica Bitnami PostgreSQL — Nodo esclavo en replicación por streaming. Soporte lectura en paralelo y redundancia.
srv-dashboard-cliente Nginx + HTML5 + Vanilla JS + Tailwind :8080 Frontend transaccional. Interfaz GLITCHPOINT para inyectar transacciones simuladas de compra.
srv-dashboard-bi Django + Jazzmin + Chart.js :8081 Panel de BI analítico. Conexión directa a PostgreSQL para renderizar KPIs ejecutivos en tiempo real.
srv-cron-backup Alpine Linux + bash — Automatiza respaldos diarios (tar.gz) de volúmenes de MongoDB y PostgreSQL en /backups/.

5. Flujo de Datos End-to-End

6. Documentación Interactiva y Contratos de API (OpenAPI/Swagger)

Uno de los pilares fundamentales en arquitecturas de microservicios modernas es la adopción de contratos de API estandarizados y autodocumentados. En el proyecto RetailSmart, el servicio srv-api-backend expone su especificación bajo el estándar OpenAPI (OAS 3.0), generada dinámicamente por FastAPI.

6.1 Exploración y Pruebas con Swagger UI (/docs)

Al acceder a http://localhost:8000/docs, el sistema presenta la interfaz interactiva de Swagger UI. Esta herramienta permite a los desarrolladores frontend, ingenieros de datos y equipos de control de calidad (QA) interactuar directamente con los endpoints expuestos sin necesidad de herramientas de terceros como Postman o cURL:

  • Inspección de Endpoints: Visualización clara de los métodos HTTP disponibles (POST /ingest para inyección de transacciones y GET /buffer para consumo por parte del worker ELT).
  • Sandbox Interactivo: Capacidad de ejecutar peticiones de prueba en tiempo real mediante el botón "Try it out", facilitando la depuración y verificación del formato de respuesta JSON (ej. {"status": "ok", "buffer_size": 1}).
  • Validación de Esquemas: Presentación explícita de los modelos de datos requeridos, incluyendo tipos de datos, campos obligatorios y ejemplos de carga.

6.2 Documentación Contractual con ReDoc (/redoc)

Para propósitos de auditoría, integración con sistemas externos (ERP/CRM de terceros) y alineación formal entre equipos de arquitectura, el backend también expone la interfaz ReDoc en http://localhost:8000/redoc. A diferencia de Swagger UI, ReDoc se enfoca en ofrecer una experiencia de lectura lineal y estructurada, ideal para adjuntar como anexo técnico en licitaciones o manuales de integración corporativa.

6.3 Pydantic y Validación de Esquemas como Firewall Automático

El contrato de API está respaldado a nivel de código por el motor de validación Pydantic. El modelo Payload define estrictamente la estructura esperada:

class Payload(BaseModel): id: str data: dict

Esta definición actúa como un firewall de datos automático. Si un cliente intenta inyectar un payload malformado (por ejemplo, omitiendo el campo id o enviando una cadena en lugar de un objeto JSON en data), FastAPI intercepta la petición antes de que alcance la lógica de negocio y retorna automáticamente un error HTTP 422 (Unprocessable Entity) con un detalle exacto del fallo de validación. Esto protege la integridad del buffer en memoria y evita la propagación de datos corruptos hacia el Data Lake.

7. Aspectos Avanzados de Infraestructura y Pruebas

Más allá de la interconexión básica de contenedores, el despliegue de RetailSmart incorpora patrones avanzados de DevOps, seguridad y aseguramiento de calidad para garantizar resiliencia en entornos de producción.

7.1 Orquestación y Prevención de Condiciones de Carrera (Race Conditions)

En arquitecturas de datos complejas, el orden de arranque de los contenedores es crítico. Si el worker de transformación (srv-etl-pipeline) intenta conectarse a PostgreSQL o MongoDB antes de que los motores de base de datos hayan completado su inicialización interna (creación de catálogos, asignación de memoria, elección de primario en Replica Sets), el contenedor fallará prematuramente.

Para solucionar esto, el archivo docker-compose.yml implementa un control de dependencias estricto mediante la directiva depends_on combinada con condition: service_healthy. Se definieron healthchecks nativos en los servicios de base de datos:

  • MongoDB Healthcheck: Ejecuta un comando de ping interno (mongosh --eval "db.adminCommand('ping')") para verificar que el nodo está respondiendo y el Replica Set rs0 ha sido inicializado.
  • PostgreSQL Healthcheck: Utiliza la utilidad pg_isready -U retail_user -d retail_dw para confirmar que el gestor está listo para aceptar conexiones en el puerto 5432.

De este modo, Docker Compose bloquea el inicio de los workers Python y del Dashboard BI hasta que las bases de datos reportan un estado 100% saludable, eliminando por completo las condiciones de carrera y los errores de conexión en el arranque.

7.2 Seguridad y Habilitación de Tráfico Cross-Origin (CORS)

En la capa de consumo, el Dashboard Cliente opera como una aplicación Single Page Application (SPA) servida por Nginx en el puerto 8080 (http://localhost:8080). Cuando el código JavaScript intenta enviar una transacción asíncrona mediante fetch() hacia el API Backend en el puerto 8000 (http://localhost:8000/ingest), los navegadores web modernos bloquean la petición por defecto debido a las políticas de seguridad de mismo origen (Same-Origin Policy).

Para viabilizar la comunicación segura, se configuró explícitamente el middleware de CORS (CORSMiddleware) en la inicialización de FastAPI:

app.add_middleware( CORSMiddleware, allow_origins=["*"], allow_credentials=True, allow_methods=["*"], allow_headers=["*"], )

Esta cabecera autoriza el intercambio de recursos entre los distintos puertos del entorno local, permitiendo que el flujo de ingesta opere fluidamente sin comprometer el aislamiento de los contenedores.

7.3 Aislamiento de Entorno y Estrategia de Pruebas Dual

Para garantizar la mantenibilidad y evitar la contaminación de dependencias en el sistema operativo host de los desarrolladores, todo el ecosistema de pruebas locales se ejecuta dentro de un entorno virtual de Python (.venv). La estrategia de validación se divide en dos frentes complementarios:

1. Pruebas Unitarias Aisladas (test_unit.py)

Se enfocan en validar la lógica interna del API Backend de forma ultrarrápida (< 1 segundo) sin depender de Docker ni de motores de base de datos externos. Utilizando FastAPI.TestClient, se simulan peticiones POST y GET directamente sobre la aplicación en memoria, verificando que los cálculos del buffer de encolado y las respuestas JSON cumplan estrictamente con el contrato esperado.

2. Pruebas de Integración End-to-End (test_integration.py)

Operan sobre la infraestructura viva. El script inyecta un payload único de prueba hacia el API expuesta en el host, espera de forma controlada los ciclos de polling de los workers ELT (5s) y ETL (10s), y finalmente ejecuta una consulta SQL remota mediante docker exec directamente contra el contenedor primario de PostgreSQL (srv-db-postgres-primary) para verificar que el registro fue correctamente persistido y transformado en la tabla fact_events. Esta prueba certifica la salud de toda la cadena de valor de datos.

7.4 Resguardo Automatizado (Servicio Cron Backup)

Para mitigar el riesgo de pérdida de datos ante corrupciones de volumen o fallos catastróficos de hardware, la arquitectura incorpora un microservicio dedicado al respaldo automatizado: srv-cron-backup.

Este contenedor, basado en una imagen ligera de Alpine Linux, monta los volúmenes físicos de MongoDB y PostgreSQL en modo de sólo lectura, junto con un directorio de salida en el host (/backups/). Mediante un script de shell programado por cron, el sistema genera diariamente archivos comprimidos (tarballs .tar.gz) con marcas de tiempo exactas. Esto asegura un punto de recuperación (RPO) de 24 horas y facilita la migración ágil de snapshots de base de datos hacia entornos de staging o almacenamiento en la nube (S3/Azure Blob Storage).

9. Reflexión Técnica y Escalabilidad

9.1 Aplicación de Streaming (Speed Layer - Arquitectura Lambda)

¿Dónde y cuándo aplicar Streaming?

En la arquitectura actual, el Streaming debe ser introducido en tres puntos críticos de la Speed Layer para complementar el procesamiento batch actual:

  • Logs de Sistema (logs_sistema.txt): Detección de anomalías y fraudes en transacciones. En producción, un stream de Azure Event Hubs conectado a Azure Stream Analytics activaría alertas automáticas en < 2 segundos para bloquear patrones sospechosos o reintentos masivos fallidos.
  • Eventos de App Móvil (eventos_app.json): Análisis de comportamiento del usuario en tiempo real. Cuando un cliente busca un producto, un pipeline de Kafka + Spark Streaming permite actualizar las recomendaciones en pantalla con latencias inferiores a 500ms.
  • Redes Sociales (redes_sociales.json): Monitoreo de sentimiento hiper-dinámico. Un comentario negativo sobre un producto en redes activa una alerta inmediata a servicio al cliente y ajusta dinámicamente el scoring del producto en el catálogo web.

9.2 Escalabilidad de la Solución Hacia Azure Cloud

Migración de Gemelo Digital a Producción Real

Esta implementación local (Gemelo Digital) está diseñada para ser 100% migrable hacia Microsoft Azure sin refactorizar la lógica de negocio ni los esquemas dimensionales:

  • Almacenamiento Local → ADLS Gen2 (Azure Data Lake Storage): Las carpetas de almacenamiento crudo migran 1:1 a contenedores ADLS Gen2, aprovechando la jerarquía de espacio de nombres y seguridad avanzada.
  • MongoDB (Data Lake) → Cosmos DB (NoSQL): El Replica Set actual se migra a Azure Cosmos DB usando la API para MongoDB. Los workers ELT mantienen su código en PyMongo intacto, modificando únicamente la cadena de conexión hacia la nube.
  • PostgreSQL (Data Warehouse) → Azure Synapse Analytics / Azure SQL DW: El modelo Star Schema y las consultas analíticas de los KPIs se ejecutan de forma nativa en Synapse, escalando el almacenamiento y cómputo de forma masivamente paralela (MPP).
  • Workers Python → Apache Spark (Azure Databricks): Los scripts autónomos de transformación se convierten en jobs de PySpark gestionados por Databricks, permitiendo procesar millones de transacciones por segundo de forma distribuida.
  • Django BI → Power BI Embedded: La capa de visualización de Chart.js se integra nativamente con tableros de Power BI embebidos directamente en el portal corporativo.

Desafíos Operativos y Estrategias de Mitigación en Producción

  • Calidad de Datos en Origen: El canal Web ocasionalmente envía transacciones con datos incompletos (ej. falta de SKU). Mitigación: Reforzar las reglas de validación en los esquemas Pydantic del API y obligar a los frontends a sanitizar el input antes del envío.
  • Saturación de Memoria en Alta Concurrencia: Ante picos de 10.000 transacciones/segundo, el buffer en memoria de FastAPI podría saturar la RAM del contenedor. Mitigación: Reemplazar la lista en memoria por un cluster de **Redis** o un topic de **Kafka** como buffer durable y desacoplado.
  • Consistencia en Replica Sets: Fallos de red durante la sincronización entre nodos primarios y secundarios pueden generar pérdida de datos enrutar a lecturas sucias. Mitigación: Configurar el write concern = "majority" en MongoDB para garantizar que el dato esté replicado en la mayoría de los nodos antes de confirmar el éxito al cliente.
  • Impacto de ETL en Consultas BI: Ejecutar transformaciones pesadas sobre el mismo motor de base de datos que atiende los dashboards puede degradar el tiempo de respuesta de la interfaz. Mitigación: Separar cargas de trabajo manteniendo una réplica de lectura (Read Replica) dedicada exclusivamente para las consultas analíticas de BI.

10. Conclusiones

La arquitectura de datos contenerizada implementada para RetailSmart Chile SA demuestra la viabilidad técnica y el enorme valor estratégico de un ecosistema moderno de microservicios. A través de la orquestación de nueve contenedores en Docker Compose, se ha construido un puente robusto entre la captura transaccional en tiempo real y la toma de decisiones ejecutivas.

Hallazgos y Logros Clave:

  • La adopción del paradigma ELT sobre un Data Lake NoSQL (MongoDB) garantiza la preservación del dato crudo histórico, permitiendo flexibilidad total para futuras reestructuraciones analíticas.
  • La integración de contratos OpenAPI y validación Pydantic en FastAPI establece un estándar corporativo de gobernanza y defensa activa contra datos malformados.
  • La gestión estricta de dependencias (depends_on + healthchecks) elimina las condiciones de carrera, garantizando despliegues automatizados y estables.
  • El análisis de los KPIs revela oportunidades claras de optimización comercial: fidelización del top 20% de clientes líderes y fortalecimiento del ticket promedio en canales digitales (Web/App).

Próximos Pasos Estratégicos:

  • Evolucionar la capa de velocidad (Speed Layer) incorporando Apache Kafka y Spark Streaming para habilitar casos de uso de analítica en tiempo real (real-time fraud detection y personalización).
  • Planificar la migración progresiva hacia Microsoft Azure (Cosmos DB, Synapse, Databricks) utilizando este proyecto como Gemelo Digital arquitectónico.
  • Implementar modelos de Inteligencia Artificial y Machine Learning sobre el Data Warehouse consolidado para transitar desde la analítica descriptiva hacia la analítica predictiva y prescriptiva.

Este informe certifica la entrega de una infraestructura de grado de producción, documentada exhaustivamente y lista para soportar el crecimiento operativo de RetailSmart Chile SA durante los próximos ciclos comerciales.
