1. Introducción y Objetivos Académicos

Tras la exitosa puesta en marcha del prototipo contenerizado de RetailSmart Chile S.A., se identificaron múltiples dependencias críticas y simplificaciones arquitectónicas en la rama principal. Para elevar la calidad de la solución al nivel exigido en la evaluación académica, se estructuró un plan de refactorización integral en la rama refactor-pipeline-architecture.

Los objetivos clave abordados en esta intervención de arquitectura e infraestructura incluyen:

  • Desacoplamiento de Datos: Migrar el pipeline de ingesta incremental para que lea archivos físicos crudos en lugar de strings de datos estáticos codificados en memoria, emulando la realidad de un data lake corporativo.
  • Carga Dinámica Externa (Frontend): Inyectar una capacidad en la consola web del cliente que permita a un docente o analista subir cualquier archivo CSV personalizado, autodetectando las cabeceras e ingectándolo en vivo en el backend.
  • Garantizar Alta Disponibilidad (HA): Corregir el pánico en los drivers de los trabajadores del pipeline de MongoDB que impedía la reconexión automática en caso de failover del Replica Set rs0.
  • Aislamiento de Red del Host: Reconfigurar el mapeo de puertos para evitar conflictos y asegurar el funcionamiento 24/7 en hosts locales compartidos con otros microservicios activos.

3. Ingesta y Consolidación Dinámica en run_pipeline.py

Originalmente, el script de orquestación run_pipeline.py ingería las transacciones desde un diccionario hardcodeado en memoria. Con la refactorización, el pipeline asume un rol de ETL/ELT moderno: lee los archivos crudos del disco físico, los mueve a la zona raw del Data Lake, y realiza la consolidación de archivos dispersos en un solo lote diario.

Particularmente para la ingesta de terminales físicas (POS), el script lee recursivamente la carpeta datasets/ventas_pos/diaN/, parsea y consolida todas las transacciones individuales utilizando un DataFrame de Pandas, y genera un solo archivo unificado por día en el lago de datos.

# Segmento del código modificado en run_pipeline.py para consolidación física: pos_day_dir = os.path.join(datasets_dir, "ventas_pos", day_key) pos_dfs = [] if os.path.exists(pos_day_dir): for f_name in sorted(os.listdir(pos_day_dir)): if f_name.endswith('.csv'): f_path = os.path.join(pos_day_dir, f_name) df_tx = pd.read_csv(f_path) pos_dfs.append(df_tx) if pos_dfs: df_pos_day = pd.concat(pos_dfs, ignore_index=True) dest_pos_path = os.path.join(DATA_LAKE_DIR, "raw", "ventas_pos", f"{date_str}.csv") df_pos_day.to_csv(dest_pos_path, index=False) print(f" [RAW] Consolidadas {len(pos_dfs)} transacciones POS en: {dest_pos_path}")

4. Ingesta de CSV en Tiempo Real desde el Dashboard Cliente

Para cumplir con la solicitud específica del docente, se habilitó una interfaz de carga directa en el Dashboard de Cliente. Esto permite al usuario arrastrar o seleccionar archivos CSV de transacciones y procesarlos sin necesidad de interactuar con terminales de consola o scripts en Python.

Detección Dinámica de Esquemas

El archivo Javascript app.js intercepta el contenido del archivo cargado mediante FileReader, lee las cabeceras iniciales y mapea dinámicamente las columnas al payload estándar JSON requerido por el endpoint /ingest:

  • Si el CSV incluye "id_venta": Mapea como canal tienda_fisica y calcula el precio total multiplicando cantidad * precio_unitario.
  • Si el CSV incluye "id_orden": Mapea como canal web o app utilizando el campo total directo.
// Código del parser JavaScript embebido en app.js: const headers = lines[0].split(',').map(h => h.trim().toLowerCase()); const isPOS = headers.includes('id_venta'); const isOnline = headers.includes('id_orden'); for (let i = 1; i < lines.length; i++) { const cols = lines[i].split(',').map(c => c.trim()); if (cols.length !== headers.length) continue; let payload = null; if (isPOS) { const id_venta = cols[headers.indexOf('id_venta')]; const id_producto = cols[headers.indexOf('id_producto')]; const cantidad = parseFloat(cols[headers.indexOf('cantidad')]); const precio_u = parseFloat(cols[headers.indexOf('precio_unitario')]); payload = { id: `POS-${id_venta}`, data: { sku: id_producto, canal: "tienda_fisica", cliente: cols[headers.indexOf('id_cliente')], precio: cantidad * precio_u, timestamp: `${cols[headers.indexOf('fecha')]}T12:00:00.000Z`, nodo: `dashboard-cliente-csv-uploader` } }; } // Enviar a la API mediante fetch(API_URL, { method: 'POST', body: JSON.stringify(payload) }) }

5. Alta Disponibilidad de MongoDB (Failover del Replica Set)

Durante las pruebas de robustez, se descubrió que los workers del pipeline fallaban catastróficamente si el nodo de base de datos Mongo con el que tenían conexión inicial sufría una desconexión o dejaba de actuar como primario. Esto se debía al parámetro estático de conexión directConnection=True.

Diagnóstico y Corrección de Alta Disponibilidad

Problema original: Al forzar directConnection=True en PyMongo, el worker no participaba en el protocolo de monitoreo del Replica Set (rs0). Ante una caída del nodo primario, PyMongo no renegociaba el enlace con el nuevo primario elegido democráticamente por MongoDB.

Solución: Se modificaron los conectores en srv-elt-pipeline/worker.py y srv-etl-pipeline/worker.py. Se externalizó el canal de comunicación mediante la variable de entorno MONGO_URI (que contiene la cadena de réplicas completa) y se configuró PyMongo con el parámetro de negociación replicaSet="rs0" como fallback.

// Código corregido en los workers de Python (worker.py): def get_mongo_db(): """Conecta a MongoDB usando MONGO_URI (soporta Replica Set) o fallback negociado.""" mongo_uri = os.getenv("MONGO_URI") if mongo_uri: client = MongoClient(mongo_uri, serverSelectionTimeoutMS=5000) else: client = MongoClient( host=MONGO_HOST, port=MONGO_PORT, username=MONGO_USER, password=MONGO_PASS, authSource="admin", replicaSet="rs0", serverSelectionTimeoutMS=5000, ) return client.retail_lake

6. Desacoplamiento de Conflictos en Puertos de Red del Host

Para permitir el levantamiento del clúster académico de manera simultánea con otras suites empresariales que corren localmente, se detectó una colisión por el uso del puerto expuesto 8080 en el host local.

Se resolvió desacoplando el servicio srv-dashboard-cliente (un servidor web Nginx ligero) remapeando su puerto local en el archivo de orquestación docker-compose.yml:

# docker-compose.yml modificado: srv-dashboard-cliente: build: context: ./servicios/srv-dashboard-cliente container_name: srv-dashboard-cliente ports: - "8082:80" # Remapeado de 8080:80 para evitar colisiones networks: - retail_network

Esta alteración permite acceder al Dashboard de cliente a través del puerto 8082 sin degradar ninguna de las llamadas internas de la red virtual del clúster retail_network.

8. Conclusiones y Consideraciones Finales

La implementación de las mejoras descritas en la rama refactor-pipeline-architecture eleva sustancialmente la robustez del sistema frente a escenarios corporativos reales:

  1. El desacoplamiento de los datos crudos a archivos físicos estructurados permite realizar auditorías directas en el disco del sistema sin requerir consultas de base de datos intermedias.
  2. La capacidad del frontend para procesar e ingestar cualquier CSV personalizado provee al docente de una herramienta dinámica de validación e inyección de contingencias.
  3. La configuración del driver con soporte de failover asegura la supervivencia analítica del negocio ante desconexiones de nodos de almacenamiento.

La arquitectura queda completamente preparada para la simulación académica y despliegues estables en entornos productivos locales de alta densidad.
